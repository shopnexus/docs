The model has three tools, all inside its sandbox: `bash` runs a command, `write` writes a whole file and `edit` replaces one exact piece of a file. It reaches ShopNexus through one of the commands bash runs, `shopnexus`, which calls the console's REST API. The agent has no API of its own: it uses the same endpoints, checks and audit log as the console. <Req id="UC-MOD-08" />

## The shopnexus command

Each command is a console operation, named by its `operationId` without "Console": `listConsoleTickets` is `shopnexus listTickets`.

```bash
shopnexus listFeedback kind=bug limit=10          # parameters are name=value
shopnexus getAccount id=0193e…                    # path parameters too
shopnexus replyTicket id=0193e… --body '{"body":"…"}'
shopnexus help listFeedback                       # the values and fields
shopnexus listTickets status=open | jq '.items | length'
```

A parameter is always `name=value`, never a `--flag`. `--body` takes JSON, or `@file` for a file in the workspace. A command prints the answer's JSON body, so the model can pipe it through `jq` or `rg`. An error answer goes to stderr with its status and the server's error body, and the command exits 1. A parameter the command lacks, or a required one left out, is refused before any call.

The command asks the server for the operations its turn may call, so a change to the API needs no new build of it. It holds no token: it talks to a socket the runtime serves, which adds the turn's token ([The runtime and its sandbox](/en/agent/runtime#ways-out)).

## The command list

The system prompt lists every command the turn may call, so the model needs no call to learn them. Each line has the command, its parameters (`?` marks an optional one), `--body` when it takes a body, `[approval]` when it is a change, and the operation's summary:

```text
listTickets status kind? cursor? limit?: The ticket queue, newest activity first.
suspendAccount id --body: [approval] Suspend a customer account.
```

A parameter's allowed values and a body's fields stay behind `shopnexus help`. The list follows the agent's capabilities and the member's role, so it reads the same on every turn of the same agent for the same role, which keeps it in the prompt cache.

## Capabilities

Every console operation in the API spec names a capability in `x-capability`:

- `none`: no agent ever calls it. Sign-in, members, the AI settings and the agent's own chats, turns and decisions are `none`.
- `turn`: every turn may call it: listing its own commands and its chat's approvals.
- anything else: the agents that hold that capability.

| Capability | Grants |
|---|---|
| `tickets.read` | The ticket queue, a ticket with its person, order and messages, the open count |
| `tickets.reply` | Replying in a ticket's chat as ShopNexus |
| `tickets.resolve` | Resolving and reopening a ticket |
| `accounts.read` | Customer accounts, one account with its identities and console history |
| `accounts.suspend` | Suspending an account and lifting the suspension |
| `reports.read` | Report cases, an account's case |
| `reports.resolve` | Dismissing, resolving and reopening an account's case |
| `orders.read` | One order with its listing, parties, shipment and tickets |
| `listings.read` | One listing with its seller, hold, reports and price guide, and its boosts |
| `listings.hide` | Hiding a listing as ShopNexus and lifting the hide |
| `feedback.read` | Feedback, a feedback item with its group, groups and the 30-day figures |
| `feedback.triage` | A group's status, hearts, joining a feedback item to a group |
| `feedback.reply` | ShopNexus's one reply to a feedback item |
| `audit.read` | The console's audit log (admins only) |
| `monitoring.read` | The system's health, metrics and logs (admins only, [System health questions](/en/agent/monitoring)) |

An admin picks an agent's capabilities in the AI settings ([Agents and settings](/en/agent/setup)). A capability that grants a change still makes only approval requests. The playground's spec shows each operation's capability.

## Roles

A turn runs as the member who asked, so what the member's role may not do, their turn may not either. The spec marks the operations only an admin may use with `x-role: admin`: today the audit log and monitoring. A moderator's turn leaves them out. They are not in its command list, `shopnexus` does not offer them, and the gate refuses them. The route's own role check would refuse them anyway, so the filter keeps the model from offering what the console would refuse.

A turn keeps the role its member had when its run started. A resume by the same member takes their role as it is then; a resume by another member keeps the turn member's role, since the turn still works for them.

## The gate

Every request with a turn token passes the same checks, in order:

<Steps>
<Step title="The token">
The token must belong to a turn that is running and not past its deadline, or the call is `401 agent_token_invalid`. It is the request's only credential: the server drops any cookie that came with it.
</Step>
<Step title="The operation">
The route must be an operation the turn's capabilities grant, and for a moderator not an admin-only one, or the call is `403 agent_operation_forbidden`. The gate looks at the operation, never at its parameters.
</Step>
<Step title="The spec">
The request is validated against the API spec, as any request is. A bad parameter or body is `400 invalid_request` with the fields at fault, which the model reads and fixes.
</Step>
<Step title="The member">
The console's guard reads the member again on every call. A member who is no longer active gets nothing, and one whose role is below the route's gets `403 console_forbidden`. The call counts against the member's own rate limit.
</Step>
<Step title="The handler">
A GET runs as the member, so the handler's own checks apply: a record the member may not see is `404`, as in the console. Any other method becomes an approval request instead ([Changes and approvals](/en/agent/approvals)).
</Step>
</Steps>

## What is recorded

Every call with a turn token is recorded with its turn, the operation, the method, the path with its query, the status it answered and how long it took. The AI settings count them per agent and operation: calls, changes held for approval, errors and the average time. <Req id="NFR-PRIV-02" />

The console's order and listing pages record a read too. They show what people wrote (tickets' last lines, reports), so each opening records the member, the record's kind and the ids it read.

| What | Kept | Then |
|---|---|---|
| A recorded call, a recorded read, a rate limit refusal | 90 days | deleted |
| A command's output in the history | 90 days | blanked; the step keeps the command |
| A chat | 180 days after its last activity | deleted with its messages, turns, events, approvals and calls |

When a user deletes their account, the server blanks the command outputs in the chat about that account. The questions, the answers and the recorded calls stay, as the console's audit log does. A sweep runs every hour.
