The agent reads data only through the server's MCP server. It serves Streamable HTTP at `/mcp` on a port of its own, apart from the API port and never behind the ingress, so nothing outside the internal network reaches it. It keeps no session: every POST is one request with its own checks, answered as JSON. A port already in use stops the server from starting, and on shutdown the server waits at most 10 seconds for calls in flight.

## Checks on every call

<Steps>
<Step title="Token">
Each call carries the MCP token as a bearer token, compared in constant time. A wrong token is 401 before any MCP handling, and the server logs `security: agent MCP call refused` without the token.
</Step>
<Step title="Moderator">
The `X-Console-Member` header carries the id of the moderator who asked. The server reads the member again on every call, so a moderator disabled between two tool calls gets nothing from the second; an unknown or disabled member is 401 too. Every role may use every tool; a tool meant for admins alone would check the role itself.
</Step>
<Step title="Tool">
A tool is a thin adapter over a module's published service; no tool reads a table. A refusal reaches the agent as a tool error with its code; any other failure reaches it as `internal error` and is logged.
</Step>
</Steps>

Every tool declares `readOnlyHint` and an input and output schema. A value from a fixed set (a ticket's status or kind, a case's status, an entity) is an enum in the input schema, taken from the owning module. A result arrives as structured content and as its JSON in one text block; ids sit under keys `id`, `*_id`, `ids` or `*_ids`, which is how the agent finds a source, and the tool's title is the label of its chip in the console.

On the agent's side, only tools with `readOnlyHint` that are on the console agent's tool list reach the model. Each call has a time limit (`tool_timeout_s`, 20 seconds by default) and is tried up to `tool_attempts` times (3 by default) on a timeout or a dropped connection, waiting half a second before the second try and twice as long before each next one, at most 4 seconds.

## Tool list

Tools that read one record take its id. List tools take `cursor` and `limit` (1 to 50, 20 by default) and answer `{items, next_cursor}`; the agent passes `next_cursor` back for the next page.

| Tool | Reads | Recorded read |
|---|---|---|
| `count` | Counts by status of accounts, listings, orders, tickets or report cases, since a date or for all time, with the total; ShopNexus's own account is left out | no |
| `lookup` | Which record an id names: an account, a report case, an order, a listing or a ticket, with the tool that reads it | no |
| `ticket_get` | A ticket, its person, its order, the first page of its chat and the person's other tickets | the ticket, its person |
| `ticket_messages` | A page of a ticket's chat, newest first | the ticket |
| `tickets_list` | The support queue: open or resolved tickets, with each chat's last line | the tickets and their persons |
| `tickets_of_account` | The newest 50 tickets an account opened, or on orders it sold | the account and the tickets |
| `account_get` | Status, age, whether it has a phone and an email (never the values), listings, orders as buyer, its suspensions; reports are left to `report_case_get` | no |
| `accounts_list` | The newest accounts, those suspended now, or the account an id or a phone number names | no |
| `orders_of_account` | An account's orders as buyer or as seller | no |
| `listings_of_account` | A seller's listings on sale or sold | no |
| `console_actions` | The console's audit log by record, by moderator or all, without IPs | no |
| `order_get` | An order, its parties, listing, price, status and the carrier's status now, read from the seller's carrier account; no recipient or pickup address; it does not read the parcel's event timeline or proof of delivery | no |
| `listing_get` | A listing in any status but deleted, as its seller sees it | no |
| `price_guide` | A listing's price against the median and size of a sample of similar listings; it takes a listing, since the sample needs the listing's vectors | no |
| `report_cases_list` | The report queue: open or resolved cases | no |
| `report_case_get` | An account's report case: reasons, listings reported, every report with its note, the resolution | the account, the reports, the reporters |

## Personal data reads

Each time a tool returns personal data (what a person wrote, messages, a ticket's person, reporters), it first writes a row to `console_agent_reads`: the moderator, the tool, the kind of subject (ticket or account), the ids it read and the time. The requirement is <Req id="NFR-PRIV-02" />. The console has no page that lists these rows yet.

## What is kept, and for how long

A sweep runs when the server starts and every hour, a batch of rows at a time:

| What | Kept | Then |
|---|---|---|
| A read record | 90 days | deleted |
| A tool call's result | 90 days | blanked; the call keeps its tool, input, status and timing, and a later run's history shows "Result no longer kept" |
| A chat | 180 days after its last activity | deleted with its turns, tool calls, events, inputs and documents |

Every write to a turn moves the chat's last activity first, and the delete skips a chat a write holds, so a running chat is never swept. When a user deletes their account, the server blanks the tool results in the chat about that account; the turns and the read record stay, as the console's audit log does.

## The order and listing pages

The console's order page (`GET /v1/console/orders/{id}`) and listing page (`GET /v1/console/listings/{id}`) are served next to the tools, for any moderator. Each reads the same facts as `order_get` or `listing_get`, through the same services, and adds what a moderator needs on one screen:

- **Order:** the buyer and the seller, the seller's sold listings and rating, the category's name, and the tickets about this order.
- **Listing:** the seller's counts, the member who hid it when it is hidden, the reports about it, and the price guide when the sample is not empty.

The tickets' last lines and the reports are what people wrote, so a page that shows any of them records the read, as a tool does. Neither page shows the parcel's event timeline or a reason for a hold. An unknown order is `404 order_not_found`, and an unknown or deleted listing `404 listing_not_found`.

## Text from users

The MCP server's instructions and the agent's system prompt both state that text users wrote (messages, notes, listing descriptions) is quoted as data only. The agent has no write tool, so an instruction hidden in that text changes no data.
