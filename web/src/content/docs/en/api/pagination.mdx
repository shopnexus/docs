List endpoints page by cursor, newest first. A request takes two optional query parameters:

- `limit`, the page size, from 1 to 100, default 20;
- `cursor`, the `next_cursor` of the previous page. Leave it out for the first page.

A page looks like this:

```json
{ "items": [ ... ], "next_cursor": "01927f3c-..." }
```

`next_cursor` is there only when more items follow. When it is missing, the list is done. `items` is always an array, empty when there is nothing.

The cursor is the ID of the last item on the page, and the next page lists the items after it. IDs are UUIDv7 and grow with time, so items created while the user scrolls do not shift the pages they already loaded. They show up on the next reload from the top.

A list sorted by something other than age, such as suspended accounts by the end of their suspension, keeps the same ID cursor. The server reads the sort value of the cursor's item and lists what comes after it.

A page carries no total. A list that needs one, such as the console's account list, adds a `total` field to its own response.

## Search

`GET /v1/search` sorts by relevance, distance or another order, not only by age. The nearby feed is one of its sorts. Its cursor is an opaque string: pass it back unchanged with the same filters. A search stops at 500 results. A cursor the server cannot read answers 400 `invalid_cursor`.

## Screens

A screen endpoint returns the first page of each list it holds. "Load more" calls the matching list endpoint with the cursor from that page and gets the same item shapes, as [Screens](/en/architecture/screens) describes.
